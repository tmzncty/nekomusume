## What was removed, and on what evidence

- **`neko_crypto::SNOW_VERSION` (`"0.10.0"`).** It **duplicates**
  `crates/neko-crypto/Cargo.toml`'s `snow = { version = "0.10.0" }` (Cargo.lock
  resolves the same 0.10.0) and **cannot be checked at runtime** - if the dependency
  is ever bumped this constant silently lies about what is linked. Removing it drops
  a value that can only go stale.
- **`neko_reliable::DEFAULT_MSS` (`1200`).** It sat among defaults that ARE used
  (`LOSS_TIME_NUMERATOR`/`DENOMINATOR` feed the loss-time formula;
  `DEFAULT_MAX_SENT_PACKETS`/`DEFAULT_MAX_FRAMES_PER_PACKET` feed
  `Recovery::default`), but `mss` is a constructor argument callers pass explicitly,
  so no code ever adopted this "default".
- **`neko_reliable::DEFAULT_MAX_ACK_RANGES` (`256`).** Same reading, and the number
  is **inconsistent with the real bound**: `PacketAckTracker` is bounded by its own
  wire-level hard cap of 32 (pinned in an earlier slice), so 256 is stale residue.

## Verification performed before removing

All three had zero references in ANY form (bare, qualified, aliased) across
`crates/**`. Neither `docs/spec/*`, other `docs/*.md` nor the README named any of
them as a contract - the only documentation hits came from the gate note itself,
which this commit updates. The clean compile afterwards is the second confirmation:
a constant still named somewhere would not build.

## Known consequence, stated explicitly

Removing a `pub` constant is a **breaking API change** for any external consumer
that referenced it. This narrows the published surface of `neko-crypto` and
`neko-reliable`. The justification is that no in-workspace code and no in-repo
document used them, and the maintainer authorised the removal.
