## The two gaps

**1. Parse failures were never distinguished from range failures.** Every numeric
flag has two failure modes with different messages: `invalid <flag>` (does not
parse) and `<flag> outside <range>` (parses out of bounds). Only the **range** mode
was asserted anywhere in the tree, so `invalid bytes`, `invalid duration`,
`invalid count` and `invalid port` were free - as was the distinction itself. The
test asserts the parse message present AND the range message absent, so a mutant
merging the two is caught.

**2. `failover-client`'s argument guards had no witness at all.** All of these run
before any socket is created and before `--server-key` is consulted, so none needs a
peer:

- `invalid UDP port` / `invalid TCP port` (unparseable, including u16 overflow)
- `ports outside 40080-40100`, both edges: 40079 / 40101 rejected, 40080 / 40100
  accepted
- `invalid first data delay` / `first data delay outside 0-2000 ms`
- `--migration-back requires --automatic-health-failover and count >= 3` - a
  **two-clause** condition, so each clause is exercised on its own (neither clause;
  failover enabled but count 2). A **CONTROL** with both clauses holding asserts the
  guard does **not** fire - without it, an always-firing guard would look pinned.
- `--cold-health-failover requires --automatic-health-failover`, same shape.

The "accepted" cases assert the run reaches the **next** guard
(`missing --server-key`) rather than a tautological success; that is what separates
`>=`/`<=` from `>`/`<` at each window edge.
