## The two survivors, measured rather than assumed

- **`PL_g2_drop_isfile`** (drop the `!metadata.is_file()` clause). It survives
  because the clause can never be the **sole** cause of rejection for any object this
  environment can produce: the temp filesystem is **ext4**, where a directory's
  `st_size` is always **4096**, and the available character devices (`/dev/null`,
  `/dev/full`) and `/proc` entries report **0**. Since `--bytes` is bounded
  **1..=1200**, `metadata.len() != bytes` already rejects every such object, so the
  `is_file` clause is **shadowed**. Recorded as unobservable here - **not** as an
  equivalence by proof: on a filesystem where a non-regular object could report a
  size inside 1..=1200 it would become observable.
- **`PL_read_msg`** (the `read_to_end` failure message). Not inducible: it needs an
  open that succeeds followed by a failing read. The one reprex found - reading a
  directory - requires `is_file` to be gone AND the directory size to equal
  `--bytes`, which cannot happen because directory `st_size` (4096) exceeds
  `MAX_BYTES` (1200).

## Addendum: the fourth message (`payload file changed or exceeds bounded --bytes`)

The commit listed this message among the gap (0 refs), so it must be accounted for
here too, even though no mutant was built for it. Its guard is

```rust
if payload.len() != bytes || payload.is_empty() || payload.len() > MAX_BYTES {
    fail("payload file changed or exceeds bounded --bytes");
}
```

and **none of its three clauses is reachable in this environment**:

- `payload.is_empty()` - `common()` rejects `--bytes 0` (`bytes == 0 || bytes >
  MAX_BYTES` -> `bytes outside 1-1200`), and the preceding guard already required
  `metadata.len() == bytes`, so a successful read yields at least one byte.
- `payload.len() > MAX_BYTES` - `bytes <= MAX_BYTES` is already enforced, the file
  length was required to equal `bytes`, and the read is capped by
  `.take((MAX_BYTES + 1) as u64)`, so the buffer cannot exceed `bytes`.
- `payload.len() != bytes` - would need the file to change size **between** the
  `metadata()` call and the `open`/`read` call. Those are consecutive statements in
  the same process with no external hook between them, so inducing it requires
  winning a filesystem race; that is not a deterministic test.

So this message stays unwitnessed, and is recorded as **not deterministically
inducible** rather than silently omitted. If it ever needs a witness, the honest
route is a test-only seam (a controllable clock/reader as used elsewhere in this
repo), which would be a production-code change and is out of scope for this guard.
