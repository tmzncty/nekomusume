## H-R9-030 — post-return stale seam consumes the real ACK obligation before the real ACK

The developer commit adds pre-ACK post-return injection code that, under `--send-stale-ack`, calls `server_rt.poll_outgoing_ack(0)` immediately after `server_rt.on_packet_received(post_pn, true)`, encodes/seals that payload, and sends it. Later, the normal Carrier-ACK block calls `server_rt.poll_outgoing_ack(0)` again.

That is not a semantic duplicate/stale injection. `PacketAckTracker::take_ack` is deliberately consumptive: one new ack-eliciting packet creates one pending ACK obligation, the first take consumes it, and a second poll yields `None` until new eligible packet evidence arrives. Therefore the first `poll_outgoing_ack(0)` under `--send-stale-ack` consumes the only current post-return ACK obligation. The datagram labeled as the stale seam is actually the first legitimate ACK for `post_pn`; the later normal Carrier-ACK block has no ACK left to send. The duplicate-after-real-ACK code nested inside that later block is consequently unreachable on this path.

This invalidates the intended oracle even before diagnosing the developer-reported crypto rejection. Marking the process test `#[ignore]` does not supply acceptance evidence and also removes the case from ordinary `scripts/check.sh` coverage.

The developer's future-ACK pre-injection does not consume `poll_outgoing_ack`, so it does not share this exact obligation-consumption defect. However its new process fixture is also ignored and therefore H-R9-029's required post-return future/rejection evidence remains unclosed.

## Minimal repair contract

Do not add a second ACK owner, second receive loop, new timeout, new malformed budget, new protocol field, new resource-policy value, or alter Session/Carrier/wire/crypto architecture.

For the post-return stale/duplicate fixture:

1. after authenticated post-return Data has called `server_rt.on_packet_received(post_pn, true)`, call `poll_outgoing_ack(0)` **exactly once** and retain that canonical current ACK plaintext;
2. send that legitimate Carrier ACK under a fresh authenticated envelope;
3. while the client operation is still active, re-seal the **same retained ACK plaintext** under another fresh authenticated envelope and send it once as the semantic duplicate/stale ACK;
4. keep the exact Session DeliveryAck pending until after the duplicate has been consumed, so the client receive owner remains alive after the first Carrier ACK has retired `post_pn`;
5. then send the exact Session DeliveryAck and allow normal dual-domain completion.

A suitable deterministic order is:

`current Carrier ACK -> re-sealed semantic duplicate -> exact Session DeliveryAck`.

This uses one canonical ACK obligation, proves the duplicate reaches Recovery only after the current packet is retired, and leaves ordinary non-test P2 behavior unchanged.

For the post-return future case, inject exactly one fresh-envelope canonical future/never-sent ACK while the same receive owner is active, then deliver the legitimate current Carrier ACK and exact Session DeliveryAck. Preserve the engine's atomic future-ACK rejection guard.
