## HIGH H-R9-025 — `r9_udp_return_packet_ack` can claim the current packet was applied when the received ACK did not retire it

The shared helper currently reduces the full `ReliableUdpRuntime::apply_ack` outcome to a boolean:

```text
applied = apply_ack(...).is_ok()
```

and returns only `UdpAcknowledgement::Carrier { applied }`.

That is not equivalent to a packet transition. `Recovery::on_ack` deliberately accepts a duplicate/stale ACK range at or below `largest_sent`; when it references only already-retired packets, the call succeeds with an empty `acked_packets` / empty resolved outcome. `PathRecovery::on_ack` explicitly treats such an empty ACK as changing nothing.

The post-return caller then emits:

```text
r9_udp_return_packet_ack applied=true packet_number=<post_pn_client>
```

where `packet_number` is copied from the locally expected post-return packet, not from the actual `RecoveryAckOutcome`. Therefore an authenticated canonical stale/duplicate ACK can produce a factually false event saying the current post-return packet was applied even while that packet remains in flight. The later loop may eventually settle correctly or fail on timeout, but the intermediate `applied=true / packet_number=<current>` evidence is already false.

This violates the R9 process/result truth requirement: an event may only claim the transition that actually occurred. It also means P2 C4 is not yet an exact dual-domain proof.

### Smallest repair contract

Do not redesign ACK framing, Session semantics, Carrier architecture, or policy values.

1. Preserve enough of the existing `RecoveryAckOutcome` through `recv_udp_delivery_ack` to distinguish:
   - canonical ACK accepted but no recovery transition;
   - actual packet(s) acknowledged/retired;
   - rejection/error.
2. For the post-return owner, only emit the positive `r9_udp_return_packet_ack` for the expected `post_pn_client` when the actual recovery outcome contains that exact packet number in `acked_packets`.
3. A valid-but-stale/empty canonical ACK must not be reported as application of the current packet. Keep it typed and bounded under the same receive owner/deadline/malformed budget; do not create another owner or retry policy.
4. Add a focused deterministic regression showing that a stale/duplicate canonical ACK can be accepted by recovery without retiring the current post-return packet and therefore cannot emit the positive current-packet transition.
5. Tighten the existing positive count=4 C4 oracle:
   - actual Session event: exactly one, `stream=1`, `offset=48`, `len=16`;
   - actual Carrier event: exactly one positive transition for the exact packet number already cross-bound by client send and server ACK generation;
   - no false/rejected shortcut;
   - `r9_udp_post_return_settled` only after both actual transitions with `remaining_in_flight=0`.

The current process test does not yet assert the newly added `len=16`, and its Carrier assertion checks only `applied=true`; it does not bind the actual client Carrier application event back to the exact packet number. Those oracle gaps should close with the repair above.
