## HIGH H-R9-010 — failed/partial Carrier settlement is still reported as “settled” and execution continues

Current flow still has a second caller phase after logical confirmations:

```text
while !outstanding.is_empty() { ... }
if let Some(rt) = rt.as_mut() {
    let settle_deadline = ...;
    while rt.in_flight() > 0 ... {
        match recv_udp_delivery_ack(...) {
            ...
            Err(_) => break,
        }
    }
    emit r9_udp_packet_ack_outcomes(... remaining_in_flight ...)
    emit r9_udp_in_flight_settled(... remaining_in_flight ...)
}
```

Any timeout, malformed-budget exhaustion, receive failure, or other classifier error in settlement merely breaks the loop. The code then emits `r9_udp_in_flight_settled` even when `rt.in_flight() > 0`, and continues into subsequent health/failover work.

This violates the committed R9-2H acceptance rule: completion requires both logical outstanding == 0 and recovery in-flight == 0; timeout before that must be an explicit bounded partial/failure, not a successful-looking “settled” event followed by continued progression.

**Required repair:** make the receive owner return a typed complete/partial/error result. Only emit `r9_udp_in_flight_settled` for `in_flight()==0`; otherwise emit an explicit partial/failure result including remaining in-flight and malformed state, and fail/stop this operation before later R9 behavior consumes a false settlement premise.

## MEDIUM M-R9-009 — one absolute receive-operation deadline still not implemented

The patch still creates:

```text
let application_deadline = ...;
...
let settle_deadline = Instant::now() + Duration::from_secs(secs.min(10));
```

So logical confirmation may consume the full original application budget and Carrier settlement can then receive a fresh extra window. The handoff explicitly required one absolute deadline established before the owner begins.

**Required repair:** use `application_deadline` (or one equivalent absolute deadline created once) for both logical confirmation and Carrier settlement. Do not create a post-confirmation extension window.
