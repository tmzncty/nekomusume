## M-R9-009 — ad-hoc recovery retry policy is not an accepted P2 repair

**Severity:** MEDIUM / acceptance-blocking. This does not independently establish a release/security HIGH.

The new loop adds two new production-path numbers — 500 ms retry cadence and `attempts >= 6` — even though the current handoff explicitly prohibited inventing a new retry numeric policy. The existing accepted readiness contract already has `READINESS_PROBE_TIMEOUT = 1 s` and `READINESS_SEQUENCE_TIMEOUT = 3 s`; P2 did not authorize a separate migration-back retry budget.

There is also a semantic limitation: the loop re-sends the **same sealed ciphertext**. `SecureSession::open_unreliable` advances a replay window after successful authentication/context validation, so if the server accepts one request but its response is lost, later copies of that same authenticated record are replay-rejected. Therefore this mechanism is not a general authenticated request retry and should not be documented or accepted as such.

Finally, “the server may still be inside its TCP readiness loop” is not by itself evidence that the original UDP request must be retransmitted: the UDP socket already exists and a tiny loopback datagram may queue until the recovery owner reads it. The current code does not establish the actual stall stage.
