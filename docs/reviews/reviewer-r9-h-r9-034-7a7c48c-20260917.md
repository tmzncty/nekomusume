## Claim challenged

An authenticated stale/duplicate Carrier ACK that Recovery accepts with an empty outcome must remain a typed non-event: no Recovery/Session mutation and no positive retirement or rejection claim. Once the repository uses `r9_udp_packet_ack_accepted_empty` as process evidence for that class, the classification must not depend on which continuation of the same bounded receive/demux owner consumes the datagram.

## Finding — HIGH evidence correctness

The existing stale process fixture now requires exactly one such event, two real positive Carrier retirements, zero typed rejection, the two Session confirmations, process success, and final Recovery zero. That closes the previously vacuous *initial-loop* proof.

However, the same operation later enters the R9 Carrier settlement continuation. In that continuation the exact-current `UdpAcknowledgement::Carrier { applied, rejected, .. }` branch still handles:

- `applied=true` by incrementing the positive count;
- `rejected=true` by incrementing/emitting rejection;

It does **not** emit the accepted-empty classification event there.

Therefore exact-current evidence is receive-phase dependent: the same authenticated accepted-empty semantic outcome is observable if consumed by the initial loop and silent if consumed by the settlement continuation. A later arrival/reorder or another bounded stale challenge may legitimately reach the settlement continuation and then disappear from process/result truth while leaving runtime state unchanged.

This is not a newly proven transport-state mutation defect. Recovery/Session semantics remain separated and accepted-empty remains a non-event. It is an acceptance-critical process/evidence defect and keeps the materially new cross-process R9 surface open for item 4.
