## H-R9-027 — HIGH acceptance/evidence false positive: the new future-ACK fixture rejects for an empty ACK range, not for `largest > largest_sent`

### Exact-current path

The new `--send-future-ack` seam constructs a canonical wire ACK with:

```text
largest_observed = u64::MAX
ranges = []
ack_delay_us = 0
```

The authenticated receive owner decodes that `AckPayload`, but converts only `ack.ranges` into `neko_reliable::AckRanges` before calling `ReliableUdpRuntime::apply_ack`. `largest_observed` is not what `Recovery::on_ack` receives.

`Recovery::on_ack` begins with:

```text
let largest = ack.largest().ok_or(Error::InvalidRange)?;
```

Only after obtaining a nonempty range maximum does it execute the future/never-sent guard against `largest_sent`.

Therefore the exact current test's empty range is rejected by the generic **empty AckRanges** precondition. It does **not** reach or prove the candidate-A invariant that a peer ACK naming a packet number greater than `largest_sent` is atomically rejected before RTT/PTO/loss/cwnd/packet-state mutation.

The process test can still observe `r9_udp_packet_ack_rejected` and pass while never exercising the intended future/never-sent branch. That makes the new regression a false-positive acceptance oracle for H-R9-026 / candidate A.

### Smallest repair contract

Do not change ACK architecture, Session semantics, crypto/wire semantics, malformed budgets, deadlines, or policy values merely to fix this test.

1. Keep the existing authenticated primary receive/demux owner.
2. Make `--send-future-ack` encode a **nonempty canonical range that itself names a never-sent packet**, for example one range `[u64::MAX, u64::MAX]` with `largest_observed=u64::MAX`. The exact value may be another deterministically proven never-sent packet number, but the range maximum reaching `Recovery::on_ack` must be strictly greater than the sender's `largest_sent`.
3. Through the process seam require one typed rejection attributable to the injected future ACK and no false positive packet transition attributable to it; legitimate ACKs must still be able to settle the real in-flight packets.
4. Add or reuse a focused deterministic lower-level `Recovery` / `ReliableUdpRuntime` regression that snapshots the existing observable recovery/CC state before the future ACK and proves it is unchanged after `InvalidRange`: sent/in-flight ownership, RTT fields, PTO count, loss/retransmit result, Reno bytes/cwnd where exposed, and Session logical state at the caller boundary. Do not invent new production observability solely for fields already directly testable below the CLI.
5. Do not require every acknowledged packet number to remain in the sent map; the invariant is only future/never-sent atomic rejection.

This is a test/evidence repair. No core protocol redesign is required.
