## Challenged invariant

The positive P2 C4 closure is supposed to prove one exact post-return reliable packet identity across all three process observations:

1. client ownership registration / send: `r9_udp_post_return_sent.packet_number`;
2. server authenticated Carrier ACK emission: `udp_return_packet_ack_sent.packet_number`;
3. client actual Recovery retirement: `r9_udp_return_packet_ack.packet_number` with `applied=true, retired=true`.

It must also prove exactly one settled-zero terminal result after both the exact Session DeliveryAck transition and exact Carrier retirement.

## Finding

The current ordinary positive fixture performs only a **two-way** packet-number bind:

- it parses `r9_udp_post_return_sent.packet_number` as `client_pn`;
- it parses `udp_return_packet_ack_sent.packet_number` as `server_pn`;
- it asserts `client_pn == server_pn`.

Later, it collects exactly one `r9_udp_return_packet_ack` and checks only `applied=true` and `retired=true`. The runtime event already contains `packet_number`, but the fixture does **not** parse it or require equality with `client_pn/server_pn`.

Therefore an incorrect client retirement diagnostic bound to the wrong packet number could still satisfy the current ordinary positive P2 oracle. Separate stale/future H-R9-032 fixtures do exercise three-way binding under their fault seams, but they do not make the ordinary no-seam P2 C4 claim exact.

The same fixture currently checks the settled-zero marker with `contains(...)` and later uses the first occurrence for ordering. It does not require **exactly one** `r9_udp_post_return_settled` event. The claimed exact C4 closure therefore also lacks settled-result cardinality.

No contradictory runtime defect is established by this review: current source emits the positive retirement event only after the actual Recovery outcome contains `post_pn_client`, and the event includes that packet number. The defect is the acceptance proof, not an observed state-machine contradiction.
